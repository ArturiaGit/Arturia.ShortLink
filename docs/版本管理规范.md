# 版本管理规范 (Versioning Guidelines)

本文档定义 **Arturia.ShortLink** 项目的语义化版本号规则、递增原则、统一发布策略与 CHANGELOG 维护流程。  
所有参与开发的贡献者（人类开发者与 AI 代理）在提交合并、发布版本、打 Git Tag、撰写 CHANGELOG 时必须严格遵守本规范。

## 1. 语义化版本 (SemVer) 基础

版本号严格采用 `MAJOR.MINOR.PATCH` 格式（完全遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/) 国际规范）：

| 位 | 名称 | 触发递增条件 | 典型场景 |
| :--- | :--- | :--- | :--- |
| **`MAJOR`** | **主版本号** | 引入**不兼容的破坏性变更** | API 契约断裂、重构删除字段、数据库不兼容迁移、架构级底层重构 |
| **`MINOR`** | **次版本号** | 引入**向下兼容的功能性新增** | 新增业务页面、新增 API 端点、新增营销套件工具、新增数据图表维度 |
| **`PATCH`** | **修订版本号**| 向下兼容的**缺陷修复与微调** | 修复已知 Bug、UI 微排版微调、优化性能、内部重构、升级补丁依赖 |

> **进位归零法则**：递增任何高位版本号时，其右侧所有低位必须立即归零。  
> 示例：`0.1.5` → 引入新特性升级为 `0.2.0`；`0.2.3` → 引入破坏性重构升级为 `1.0.0`。

## 2. 核心原则：最小递增原则 (Minimal Bump)

> 🎯 **口诀**：**能升 PATCH 就不升 MINOR，能升 MINOR 就不升 MAJOR。**

版本号是对外部使用者与协同团队的严格契约承诺，夸大版本递增会人为放大升级心智成本与维护风险。

1. **默认动作是 PATCH**：
   * 凡未引入“用户可直接感知的新功能”、未破坏既有业务行为的改动，一律按 PATCH 递增。
   * 修整文案、对齐间距、提升图表渲染帧率、重构 Mock 内部持久化逻辑均属于此类。
2. **MINOR 仅在“交付新业务能力”时递增**：
   * 仅在提供用户/客户端可直接调用或使用的新功能时递增。如：工作台新增二维码导出、新增 UTM 构建器、新增工作空间成员邀请界面等。
3. **MAJOR 仅在“不升级就会断裂故障”时递增**：
   * 前后端数据结构破坏性改动、数据库历史字段直接删除导致旧代码无法解析、认证机制完全推倒重来等。
4. **决策裁决顺序**：
   * 遇到版本定夺疑虑时，按照 **PATCH → MINOR → MAJOR** 顺序逐级自查，取满足要求的最低级别版本位。

### 2.1 0.x 阶段特殊规则 (Pre-1.0 Phase)

* **起步版本**：本项目起步版本定义为 **`0.1.0`**，代表“基础原型规范与骨架确立，功能持续迭代中，对外 API 契约尚在成形”。
* **0.x 的破坏性兼容例外**：
  * 依据 SemVer 官方规范，`0.x` 阶段的软件处于快速孵化期，**MINOR 递增允许包含破坏性变更**（即 `0.x` 下的 MINOR 变动承担了 1.0 后的 MAJOR 职能）。
  * 但必须做到：在 Commit 中显式附注 `BREAKING CHANGE`，并在 [CHANGELOG.md](../CHANGELOG.md) 中用高亮警示框详细列出破坏点与前后端调整指引。
* **`1.0.0` 正式版发布触发条件**（满足其一即应正式发布 1.0.0）：
  1. 前后端 API 契约与 MySQL 数据库结构全面冻结，正式承诺对外向后兼容。
  2. 《功能开发清单.md》中阶段一至阶段八的全部 MVP 功能端到端跑通，完成生产就绪测试验收。

## 3. 全工程统一版本号策略 (Unified Versioning)

本项目的前端（React Web）与后端（.NET 10 WebAPI）**共用同一个全局版本号，并同步发布**。

### 3.1 统一版本号的战略理由
前端与后端之间存在强烈的 API 接口契约依赖。若前端与后端各自维护独立版本号（如前端 `v0.4.0` 对接后端 `v0.2.1`），会快速催生一张复杂混乱的兼容性对照矩阵；  
**统一版本号意味着极简的承诺：“同版本号的前端与后端绝对互相兼容”**。

### 3.2 版本号唯一定义源 (Single Source of Truth)

| 模块 | 版本落地与同步机制 |
| :--- | :--- |
| **唯一权威源** | 前端根目录 `package.json` 的 `"version"` 字段为全局主版本源 |
| **.NET 10 后端** | 后端在 `.csproj` 或 `Directory.Build.props` 中配置 `<Version>` 节点，与前端保持同步 |
| **Web 界面展示**| 前端构建时通过 Vite `define` 环境变量注入版本号，在控制台底部极简展示（如 `v0.1.0`） |
| **后端 API 暴露** | 后端只读健康检查接口 `GET /api/v1/system/version` 返回该统一版本号 |
| **Git Tag** | 由 `main` 分支统一打出 `v{version}`（如 `v0.1.0`）全局 Tag |

## 4. 变更影响面与发版等级速查表

发布前请通过下表快速裁决本次更新应该递增的版本位：

| 变更内容与业务场景 | 对应版本位 | 操作说明 |
| :--- | :---: | :--- |
| Bug 修复、样式与间距微调、注释调整、内部代码重构、依赖安全补丁升级 | **PATCH** | 日常质量维护，低风险 |
| 新增短链营销工具（如新增二维码 Logo 嵌入、新增 UTM 构建器） | **MINOR** | 向下兼容的新特性 |
| 新增 API 接口端点（原有接口入参和出参保持完全兼容） | **MINOR** | 向下兼容的新接口 |
| 数据库新增表、新增非必填字段、新增索引优化 | **MINOR** | 向下兼容的数据库扩充 |
| 修改或删除已有 API 字段、修改统一响应体结构、修改 HTTP Header 传参方式 | **MAJOR**<br>*(0.x 期: MINOR)* | 破坏性契约变更，需显式声明 `BREAKING CHANGE` |
| 数据库删除已有字段、重命名关键唯一索引导致历史代码写入失败 | **MAJOR**<br>*(0.x 期: MINOR)* | 破坏性数据变更 |
| 仅修改 `docs/` 规范文档、说明文件或开发辅助工具 | **不发版** | 纯工程维护，不打 Git Tag，不递增软件版本号；但必须在对应文档自身文首追加文档修订记录 (Doc SemVer) |

## 5. Git Tag 与 CHANGELOG 维护规范

### 5.1 Git Tag 规范
1. **命名格式**：统一采用 **`v{MAJOR}.{MINOR}.{PATCH}`**，例如 `v0.1.0`、`v0.2.0`、`v1.0.0`。
2. **打 Tag 分支约束**：**Tag 只能且必须在 `main` 分支上打**，严禁在临时特性分支或未合并代码上打 Tag。
3. **强制使用附注标签**：必须使用带有说明的附注 Tag（Annotated Tag）：
   ```bash
   git tag -a v0.1.0 -m "release: 发布 v0.1.0 首个 MVP 版本"
   git push origin v0.1.0
   ```

### 5.2 CHANGELOG.md 编写格式规范

版本 Tag 必须与根目录 `CHANGELOG.md` 保持严格的一一对应关系。  
变更日志遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.0.0/) 标准，包含以下标准小节：

* **Added (新功能)**：新增加的业务功能或交互。
* **Changed (功能变更)**：对既有功能的调整或行为改变。
* **Fixed (缺陷修复)**：修复的问题及关联 Issue 编号。
* **Removed (移除功能)**：本次移除的废弃功能。
* **Security (安全加固)**：针对漏洞或风控的修复升级。

#### 标准 CHANGELOG 格式范本：

```markdown
# 变更日志 (CHANGELOG)

本工程遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/) 语义化版本规范。

## [0.1.0] - 2026-09-06

### Added
- 初始化全套架构规范与开发基准文档（需求文档、功能清单、UI 规范、接口契约、数据库设计）。
- 完成前端 React + Vite + Tailwind CSS + shadcn/ui 基础架构搭建。
- 新增本地高保真 Mock 数据服务引擎，支持全生命周期离线交互。
- 实现工作台仪表盘、短链快捷生成与二维码定制核心组件。
```
