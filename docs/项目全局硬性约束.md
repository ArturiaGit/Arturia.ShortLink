# 项目全局硬性约束规范 (Project Global Hard Constraints)

本文档定义 **Arturia.ShortLink** 项目的不可协商红线与最高工程法则。  
**任何开发行为（包括 AI 代理的自动代码生成与人类开发者的修改）触碰以下任何一条红线，即为一票否决的严重违规，必须立即撤销重置**。若业务演进确实需要突破红线，唯一途径是先经人类开发者提议并修订本文档。

## 1. 第一条红线：技术栈绝对锁定 (Tech Stack Lock)

以下选型为本项目的工程基石，**擅自引入非标替代方案或更换任一项属于 MAJOR 级重大违规**：

| 领域 | 锁定技术选型 | 严禁行为 |
| :--- | :--- | :--- |
| **前端工程** | React 19 + TypeScript + Vite + Tailwind CSS | 严禁私自更换为 Vue / Angular / 原生 JS |
| **前端 UI 体系** | shadcn/ui (New York 风格) + Radix UI + Lucide Icons | 严禁引入 Ant Design / Element / MUI / Mantine 等外部重型 UI 库 |
| **前端图表** | `recharts` (灰阶渐变微质感) | 严禁引入非标高复杂度重量级商业图表库 |
| **后端核心** | .NET 10 + C# ASP.NET Core WebAPI | 前端 Agent 严禁编写任何后端代码；后端由独立后端开发 Agent 依据规范构建 |
| **持久化存储** | MySQL 8.0.46（默认 `utf8mb4_unicode_ci`，Slug 使用 `ascii_bin`） | 开发、测试与部署禁止浮动 MySQL 标签；严禁私自改为 MongoDB / SQLite 等非指定数据库 |
| **MVP 异步与缓存** | `System.Threading.Channels` + MySQL | MVP 严禁私自加入 Redis、RabbitMQ、ClickHouse 等运行时依赖；演进前必须先修订规范并获批 |
| **包管理** | npm (遵循 Node ≥ 20 环境) | 严禁在工程内混用非标包管理器产生脏锁文件 |

## 2. 第二条红线：三 Agent 专职分工、研读前置与双轨 PR 隔离 (Tri-Agent Boundaries & Dual-Track PR)

1. **三 Agent 专职角色界限**：
   * **前端 Agent**：100% 仅负责前端工程（组件、页面、交互、样式、本地 Mock 服务），严禁编写任何 C# 后端代码。
   * **后端阶段详细设计 Agent**：专职负责各大阶段实施前的深度架构对齐与详细技术方案设计；通过 `/grill-me` 裁决技术分支，输出《阶段详细设计说明书.md》，并在文末附录与会话中输出针对开发 Agent 的标准化执行 Prompt。
   * **后端开发 Agent**：专职负责后端工程代码与测试落地；必须**先研读宏观阶段文档与契约，再深入研读本阶段具体实施方案**，完全理解后方可切出分支开工。
2. **资产双轨 PR 隔离红线 (Dual-Track PR Lifecycle Rule)**：
   * **阶段专属资产**（阶段详细设计说明书、后端源码、测试、阶段清单勾选及业务开发中微调的本阶段对应接口契约）：保留在本地工作区与阶段特性分支中，无需提前单独提 PR，随该阶段全部代码自测与验收通过后，在同一个阶段 PR 中统一合入 `main`。
   * **全局 / 跨阶段规范资产**（`AGENTS.md`、`README.md`、`LICENSE`、`Git工作流与Commit规范.md`、`项目全局硬性约束.md` 等全局宪法）：一旦在阶段准备或评审中发生新增或修改，**必须先单独切出 `docs/<name>` 分支提交 PR 提前合入 main**，绝不允许滞留在业务特性分支中延误生效。
3. **跨 Agent 双向文档同步协议**：
   * 前端 Agent 每次完成一个前端大阶段，必须审查接口与 Mock 逻辑，**同步更新《接口契约规范.md》与《后端详细设计与技术实现说明书.md》**，并在《后端功能开发清单.md》中同步前置状态。
4. **Mock-First 独立闭环承诺**：
   * 前端目前的一切数据与业务请求，**必须且只能由前端本地高保真 Mock 服务引擎驱动**（通过 `VITE_USE_MOCK=true`）。
   * 前端在完全脱离真实后端服务器的条件下，**必须能够 100% 独立运行并闭环体验全部增删改查、工作空间切换、图表联动与交互反馈**。

## 3. 第三条红线：零手搓 UI 与标准原子组件 (Zero Handcrafted UI)

所有前端业务代码必须严格遵守 [docs/前端UI设计规范.md](./前端UI设计规范.md)，触犯以下任何一项立即打回：

1. **严禁手写原生交互标签**：
   * 严禁在业务页面中使用原生 `<button>`、`<input>`、`<select>`、`<textarea>`；必须统一从 `@/components/ui/` 引入标准原子组件。
2. **严禁硬编码 HEX 颜色值**：
   * 严禁在 Tailwind 类名中手写硬编码 HEX 色值（如 `bg-[#18181b]`、`text-[#10b981]`）；必须统一使用 Tailwind 语义变量（`bg-background`、`text-foreground`）或标准的 Zinc 冷灰色阶。
3. **高危操作必须拦截**：
   * 删除短链、解绑域名、撤销密钥等破坏性操作，**严禁使用原生 `window.confirm`**；必须使用 `@/components/ui/alert-dialog` 弹出规范的二次确认对话框。
4. **表单强制类型安全**：
   * 严禁使用裸 `useState` 分散管理复杂表单字段与手动报错；必须统一采用 `react-hook-form` + `zod` + shadcn `<Form>` 标准范式。
5. **站内跳转严禁原生 `<a>` 标签**：
   * 内部页面与路由跳转必须使用路由库跳转组件，严禁手写原生 `<a>` 标签引发整页刷新与白屏闪烁。

## 4. 第四条红线：人机协同大阶段审阅、PR 与自动合并 (Human-in-the-Loop)

为确保 AI 代理开发方向 100% 可控、远端 Pull Requests 链路规范可溯，严格执行 [docs/Git工作流与Commit规范.md](./Git工作流与Commit规范.md) 第 5 节的闭环铁律：

```text
[前置工作区纯净检查 ＆ 主干变基同步 ＆ 切出特性分支] ──► [完成大阶段开发] ──► [自动调浏览器唤起页面] ──► [等待用户人工审阅]
                                                                                                            │
                                                                                                            ▼
[Agent原地暂停] ◄── [同步main并验净] ◄── [Squash合并PR] ◄── [创建PR] ◄── [提交推送] ◄── [特性分支勾选清单并复验] ◄── [用户明确同意]
```

1. **必须前置纯净基线与分支切出**：
   * 启动任一大阶段开发前，先以 `git status --porcelain` 校验工作区。除针对本大阶段的《阶段详细设计说明书.md》（`docs/阶段详细设计/`）或清单初步标记在暂存区外，**存在其他未受控的杂乱改动时严禁拉取或切换分支**，必须停手报警由人类处理；
   * 确认工作区就绪后，若暂存区包含本阶段设计说明书，直接从最新 `main` 切出独立特性分支（`feat/phase-X-<name>`）并继承该暂存修改；各大阶段设计说明书属于该大阶段交付物的有机组成部分，无需提前单独提 PR，允许随本阶段特性分支代码和测试在最终同一个阶段 PR 中统一合入；
   * **冲突一票否决**：若主干拉取或分支操作发生冲突，必须自动执行 `git rebase --abort` 彻底恢复现场并停手向人类报警，严禁私自强行解决。
2. **必须按大阶段颗粒度执行**：前端 Agent 严格以《前端功能开发清单.md》（阶段一至阶段八）为交付基准；后端 Agent 严格以《后端功能开发清单.md》（阶段一至阶段五）为交付基准，严禁自行合并或拆碎大阶段。
3. **必须主动呼起浏览器**：前端大阶段就绪后打开 `http://localhost:5173`；后端大阶段构建与测试通过后启动 API 并打开 `http://localhost:5000/scalar/v1`，供人类审阅。
4. **严禁擅自越权提交推送**：在未获得人类用户明确的确认同意前，**绝对严禁执行 `git commit` 或 `git push`**。
5. **确认后先勾选与复验**：用户明确同意后，Agent 先在特性分支勾选对应阶段清单、**同步更新根目录 `AGENTS.md` 文首的「当前进度」摘要**、更新清单修订记录并复跑全部门禁；用户批准前不得勾选，合并后不得直接在 `main` 补写。
6. **复验后自动推送与创建 PR**：最终门禁通过后，Agent 在特性分支执行代码暂存、Conventional Commits 规范提交、推送到远端特性分支，并使用 `gh pr create` 自动创建 GitHub Pull Request。
7. **自动命令行 Squash 合并与主干同步**：PR 创建成功后，Agent 自动调用 `gh pr merge --squash --delete-branch` 完成远程合并与分支清理，并切回 `main` 拉取最新代码，验证清单已合入且工作区纯净。
8. **合并后必须原地暂停**：验证完成后，Agent **必须立即停止调用任何工具并原地暂停**，向用户报告当前阶段成果，静候下一阶段指令。

## 5. 第五条红线：核心业务安全与风控底线 (Security & Abuse Prevention)

1. **协议严格白名单**：
   * 目标长链接仅允许合法 `http://` 与 `https://` 协议；前端与后端表单校验必须坚决拦截 `javascript:`、`data:`、`file:` 等一切潜在 XSS 与伪协议。
2. **绝对禁止自环递归**：
   * 严禁将短链服务平台自身的域名（如 `art.link`、`*.art.link`）作为目标长链接进行缩短，彻底防范恶意死循环重定向造成的服务雪崩。
3. **敏感词与黑名单阻断**：
   * 输入命中违规黑名单关键词或恶意域名的链接时，前端必须即时阻断创建并给出醒目的风控警告提示。
4. **凭据安全与密码脱敏**：
   * 短链访问保护密码严格使用不可逆哈希（BCrypt）存储；
   * API Key 明文仅在创建瞬间展示一次，严禁写入日志，数据库仅保留 SHA256 哈希值与前缀；
   * 严禁将任何真实密钥、Token 或数据库密码硬编码或提交入 Git 仓库。

## 6. 第六条红线：文档与代码同步约束 (Docs As Single Source of Truth)

> 🎯 **口诀：代码与文档不一致视为严重 Bug。**

1. **唯一执行准绳**：
   * 前端 Agent 严格以 [docs/前端功能开发清单.md](./前端功能开发清单.md) 为唯一事实依据；后端 Agent 严格以 [docs/后端功能开发清单.md](./后端功能开发清单.md) 与 [docs/后端详细设计与技术实现说明书.md](./后端详细设计与技术实现说明书.md) 为唯一事实依据；
   * **严禁跑偏、严禁漏项、严禁擅自凭空新增未经清单列入的功能**。
2. **同步更新前置铁律与跨端同步**：
   * 后续在研发或体验中若有任何新需求、功能变更或交互调整，**必须先同步修订《需求规格说明书.md》与对应清单**，并在获得用户确认后方可动手编码。
   * 前端 Agent 交付前端阶段时，若涉及接口行为或 Mock 规则调整，必须同步修订《接口契约规范.md》与《后端详细设计与技术实现说明书.md》。
3. **文档修订流水刚性记录**：
   * 凡对 `docs/` 规范文档进行任何实质性新增、修改或微调，**必须在同一次提交中同步更新该文档文首的「文档概述与修订记录」表格**。
   * 严禁裸改正文而不记流水；修订记录必须如实记录文档版本号（Doc SemVer）、修订日期、修订人/Agent 与改动要点。

## 8. 第八条红线：统一版本管理与最小递增 (Minimal Bump Versioning)

1. **全工程统一版本号**：
   * 前端与后端共用单一版本号（根目录 `package.json` 的 `"version"` 为全局主真实源），Tag 统一为 `v{version}`，严禁前后端私自维护独立版本号导致兼容性矩阵混乱。
2. **最小递增原则 (Minimal Bump)**：
   * **能升 PATCH 就不升 MINOR，能升 MINOR 就不升 MAJOR**。
   * 日常 Bug 修复、样式排版对齐、内部重构一律递增 **PATCH**；
   * 仅在交付“用户可感知的新功能模块”时递增 **MINOR**；
   * 破坏性契约变更在 0.x 阶段递增 MINOR 并在 Commit 与 CHANGELOG 中显式标注 `BREAKING CHANGE`。
